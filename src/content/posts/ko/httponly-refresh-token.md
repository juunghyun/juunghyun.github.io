SSO 이슈를 하나 받았다. 받고 나서 처음 든 생각은 이거였다.

SSO가 정확히 뭐지?

나는 백엔드 개발자다. 그런데 이번 일은 프론트엔드 레포(Next.js)에 있었고, 내용은 로그인 쿠키를 다루는 일이었다. 한 줄로 줄이면 "refreshToken을 HttpOnly 쿠키로 바꾼다"다. 쿠키 속성 하나다. 이걸 하는 데 사흘이 걸렸다. 첫날은 거의 공부만 했다. (개념부터 채워야 설계가 가능하니)

그리고 배포한 뒤에, 내가 만든 구조에서 문제를 하나 더 찾았다. 이 글은 그 둘의 기록이다.  
같은 구조를 가진 서비스는 많고, 여기 나오는 문제도 그 구조에서 흔히 나오는 것들이다.

## SSO, 짧게

SSO(Single Sign-On)는 한 번 인증한 결과를 여러 서비스가 믿고 쓰게 하는 구조다. 로그인을 맡은 인증 서버가 토큰에 서명하고, 각 서비스는 그 서명만 검증한다. 사용자는 비밀번호를 한 번만 넣고, 조직은 인증을 한 곳에서 관리한다. 서비스마다 인증을 따로 두면 가장 약한 서비스가 전체 보안 수준을 정한다는 게 당근이 인증을 한 곳으로 모은 이유였다([당근의 인증은 어떻게 달라져 왔을까요?](https://medium.com/daangn/%EB%8B%B9%EA%B7%BC%EC%9D%98-%EC%9D%B8%EC%A6%9D%EC%9D%80-%EC%96%B4%EB%96%BB%EA%B2%8C-%EB%8B%AC%EB%9D%BC%EC%A0%B8-%EC%99%94%EC%9D%84%EA%B9%8C%EC%9A%94-a50dd4b7b44c)).

만드는 방식은 크게 둘이다. 인증 서버가 루트 도메인에 쿠키를 심어 형제 서비스가 같이 받게 하거나, 인증 서버에 다녀오면서 1회용 코드를 받아 와 토큰으로 바꾼다(OAuth2, OIDC). 앞의 방식은 인증 서버와 서비스의 등록 도메인이 같아야 하고, 도메인이 다르면 브라우저의 서드파티 쿠키 차단에 걸린다. Wikimedia가 도메인이 다른 위키들 사이의 로그인을 페이지 이동 방식으로 바꾼 것도 이 때문이다([SUL3](https://www.mediawiki.org/wiki/MediaWiki_Platform_Team/SUL3)).

내가 맡은 서비스는 인증 서버와 등록 도메인이 달랐고, 두 번째 방식을 쓰고 있었다.

## 내가 한 일

바꾸기 전 로그인은 이랬다.

```
1. 인증 서버가 1회용 코드를 URL에 붙여 서비스로 돌려보낸다
2. 브라우저 JS가 그 코드를 토큰으로 바꾼다                → 인증 서버
3. 브라우저 JS가 응답의 accessToken, refreshToken을 document.cookie로 저장한다
```

문제는 3번이다. refreshToken은 accessToken을 계속 새로 발급받을 수 있는 토큰이다. 이걸 JS가 직접 쿠키에 썼다. JS가 쓸 수 있는 쿠키는 JS가 읽을 수도 있다.

바꾼 흐름은 이렇다.

```
1. (같음)
2. 브라우저가 코드를 같은 오리진의 서버 라우트로 보낸다
   → 서버가 인증 서버에서 토큰으로 바꾼다
3. 서버가 refreshToken을 Set-Cookie: HttpOnly; Secure; SameSite=Lax 로 심는다
   응답 본문에는 accessToken만 담는다
```

HttpOnly 쿠키는 JS가 지울 수도 없다. 기존 로그아웃은 JS가 `document.cookie`로 쿠키를 지웠는데, 그대로 두면 삭제가 거부되어 로그아웃했는데도 refreshToken이 남는다. 다음 페이지 이동 때 서버가 그걸로 다시 로그인시킨다. 로그아웃이 안 되는 로그아웃이다. 그래서 지우는 일도, 열린 탭에서 토큰을 재발급하는 일도 같은 오리진의 서버 라우트로 옮겼다. 쿠키를 심고, 읽고, 지우는 일이 한 서버에 모였다.

교환을 서버로 옮기면 인증 서버가 보는 호출자가 브라우저에서 서버로 바뀐다. 그래도 되는지는 내가 정할 수 없는 문제라, 착수 전에 인증 서버 팀에 질문을 보냈고, 돌아온 답 하나로 설계가 정해졌다!

### 무엇을 막았고, 무엇이 남았나

XSS(사이트에 악성 스크립트가 주입되는 공격)가 나도 refreshToken은 못 가져간다. 두 토큰을 훔쳤을 때를 비교하면 차이가 분명하다.

|               | refreshToken 탈취                               | accessToken 탈취                      |
| ------------- | ----------------------------------------------- | ------------------------------------- |
| 할 수 있는 일 | 새 accessToken을 계속 발급받는다. 열쇠 복사기다 | 그 토큰으로 API를 부른다. 열쇠 하나다 |
| 기간          | refresh가 만료될 때까지. 길다                   | 남은 수명. 짧다                       |

단, 두 가지가 남는다.

첫째, accessToken은 여전히 JS가 읽는다. API는 `Authorization: Bearer` 헤더로 인증하고, 그 헤더는 JS가 토큰을 읽어서 만든다. accessToken까지 HttpOnly로 바꾸면 API 호출이 전부 깨진다. 그리고 XSS가 페이지 안에서 돌고 있는 동안에는 토큰을 훔칠 필요조차 없다. 사용자 대신 요청을 보내면 된다. HttpOnly가 막는 건 "가져가서 다른 곳에서 쓰기"까지다.

둘째, CSRF는 HttpOnly가 막는 공격이 아니다. CSRF는 다른 사이트가 사용자의 브라우저를 시켜 요청을 보내게 하는 공격이고, 브라우저는 그 요청에 쿠키를 알아서 싣는다. HttpOnly여도 싣는다.

accessToken까지 브라우저에서 치우려면 모든 API 호출을 프론트 서버가 대신 전달하는 전면 BFF(Backend for Frontend)가 필요하다. 티켓 하나의 범위를 넘는다. 그래서 이번에는 오래 사는 열쇠 복사기만 치우고, 짧게 사는 열쇠 하나는 받아들인 위험으로 PR에 적어 뒀다. 나중에 "이건 왜 안 막았냐"는 질문이 오면 답할 수 있도록.

## 배포하고 나서 찾은 문제

검증 환경에서 쿠키가 HttpOnly로 찍히는 걸 확인한 김에, 콘솔에서 재발급을 두 번 동시에 불러 봤다. 콘솔에서 직접 부르면 앱에 있는 중복 방지를 거치지 않아서, 탭 두 개가 동시에 재발급하는 상황을 흉내 낼 수 있다.

```js
// refreshToken 쿠키로 accessToken을 다시 받는 요청
const refresh = () =>
  fetch("<재발급 라우트>", { method: "POST" }).then(r => r.status);

// 같은 요청을 동시에 두 번 보낸다
Promise.all([refresh(), refresh()]).then(console.log); // [401, 200]
```

하나는 성공하고 하나는 401이다. 그리고 쿠키 저장소에서 refreshToken이 사라져 있었다.

### 왜 생겼나

세 가지가 겹쳤다.

1. **인증 서버는 재발급할 때마다 refreshToken도 새것으로 바꿔 준다(회전).** 방금 쓴 옛 토큰을 다시 내밀자 거절했다.
2. **중복 방지가 탭 하나 안에서만 동작했다.** "지금 재발급 중"을 변수 하나로 기억했는데, 변수는 탭마다 따로다. 쿠키는 브라우저의 모든 탭이 같이 쓴다.
3. **내가 만든 라우트가 401을 "토큰이 죽었다"로 읽고 쿠키를 지웠다.**

```
시작 쿠키 R0
탭 A: R0로 재발급 → 성공, 새 쿠키 R1 저장
탭 B: 아직 R0로 재발급 → 401, 쿠키 삭제
→ B의 응답이 A보다 늦게 도착하면 R1까지 사라진다
```

3번은 내가 일부러 넣은 규칙이었다. 일시 장애 때 쿠키를 지우면 멀쩡한 탭까지 끊기니, 인증 서버가 분명히 거절한 경우에만 지우자는 것이었다. 그런데 경합에서 진 쪽의 401은 토큰이 죽었다는 뜻이 아니다. 방금 다른 탭이 새것으로 바꿨다는 뜻이다. 경합할 구조는 원래 있었고, 내 규칙이 그 피해를 "모든 탭 로그아웃"으로 키웠다.

### 왜 첫 설계에서는 보이지 않았을까?

- **요청을 하나씩만 봤다.** 설계와 검증은 "이 요청이 오면 무엇을 돌려주는가"를 확인했다. 거부 조건, 쿠키 속성, 로그아웃까지 요청 하나하나는 전부 맞았다. 두 요청이 겹치는 순서는 확인 목록에 없었다.
- **탭 하나에서는 일어나지 않는다.** 탭 안의 중복 방지가 막아 준다. 탭을 여러 개 띄워 두고 한꺼번에 깨워야 겹치는데, 개발하고 확인하는 동안에는 그럴 일이 없었다.
- **지워진 순간에는 티가 나지 않는다.** accessToken이 아직 살아 있어서다. 그게 만료되는 시점에야 모든 탭의 재발급이 한꺼번에 실패한다. 원인과 증상이 떨어져 있어서, 사용자에게는 "가끔 이유 없이 로그아웃된다"로 보인다.

토큰이 새는 문제가 아닌 세션이 끊기는 문제다.

일부러 두 번 쏘지 않아도 일어나는지 따져 봤다. 탭이 하나면 거의 안 난다. 탭을 여러 개 띄워 두고 노트북을 덮었다 열거나 네트워크가 다시 붙을 때가 가장 겹치기 쉽다. 모든 탭이 한꺼번에 깨어나 다시 조회하기 때문이다. 검증 환경 로그에도 일반 사용 중에 겹친 흔적이 있었다.

### 어떻게 고칠 것인가

두 곳을 같이 고친다.

- **재발급을 탭 사이에서 한 줄로 세운다.** 브라우저의 [Web Locks API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API)(`navigator.locks`)는 같은 오리진의 탭들이 락 하나를 나눠 쓰게 해 준다. 락을 얻은 탭만 재발급한다. 기다렸다가 락을 얻은 탭은 그사이 다른 탭이 이미 갱신했는지 먼저 보고, 갱신돼 있으면 재발급을 건너뛴다. 앞 탭이 멈춰도 뒤 탭이 영영 기다리지 않도록 대기 시간에 상한을 둔다.
- **재발급의 401에서는 쿠키를 지우지 않는다.** 쿠키를 지우는 건 로그아웃과 세션 만료 때뿐이다. 정말 죽은 쿠키가 남아도 다음 로그인이 덮어쓴다. 401을 받은 쪽은 잠깐 뒤에 한 번만 다시 시도한다. 그사이 쿠키가 새것으로 바뀌었을 수 있어서다.

이걸로 다 닫히지는 않는다. 락은 브라우저 안의 약속이다. 페이지를 이동할 때 서버에서 도는 재발급은 이 락에 참여할 수 없어서, 그쪽과 탭이 겹치는 경우는 남는다. 다만 쿠키를 지우지 않으니 다른 탭은 멀쩡하고, 진 쪽만 로그인 화면을 한 번 거친다. 인증 서버의 세션이 살아 있으면 그대로 돌아오고, 아니면 다시 로그인한다.

확인할 것도 하나 남았다. 인증 서버가 옛 토큰의 재사용을 감지했을 때 어디까지 폐기하는지다. OAuth 보안 권고([RFC 9700](https://www.rfc-editor.org/rfc/rfc9700))는 회전하는 refresh token이 다시 쓰이면 인증 서버가 탈취 신호로 보고 살아 있는 토큰까지 폐기한다고 설명한다. 인증 서버가 그렇게 동작한다면 이긴 쪽의 새 토큰도 함께 죽고, 클라이언트 쪽 수정만으로는 다 막지 못한다. 인증 서버 팀에 물어볼 질문이다.

수정은 미리 만들어 두었고, 임시 하네스에서 탭 여러 개 시나리오로 확인했다. 위 질문의 답을 받은 뒤 내보낼 생각이다.

## 그 과정에서 배운 개념

첫날 공부한 것과 경합을 풀면서 알게 된 것을 한 줄씩만 적는다.

| 개념                      | 내가 배운 것                                                                                                                                                   |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| origin과 site             | 서브도메인만 달라도 origin은 다르다. 그래서 CORS에 걸린다. 그런데 쿠키는 등록 도메인만 같으면 같은 편으로 친다. 기준이 둘이라는 걸 몰랐다..                    |
| 쿠키를 심는 두 길         | "JS가 쿠키를 심는다"는 말부터 이해가 안 됐다. 서버가 응답 헤더로 심는 길과, 브라우저에서 도는 JS가 `document.cookie`에 쓰는 방법이 따로 있다.                  |
| HttpOnly                  | 쿠키의 종류인 줄 알았는데 속성이다. 서버가 심을 때만 붙일 수 있고, 붙으면 JS는 읽지도 지우지도 못한다. 요청에는 그대로 실린다!                                 |
| 쿠키의 신원               | 이름이 같아도 Domain이나 Path가 다르면 다른 쿠키다. 지울 때도 심을 때와 똑같이 적어야 지워진다.                                                                |
| SameSite                  | 다른 사이트에서 넘어온 요청에 이 쿠키를 실을지 정하는 값이다. Lax로 둬야 메일 링크나 로그인 서버에서 돌아올 때 로그인이 유지된다.                              |
| 서드파티 쿠키 차단        | 서버 설정이 아니라 브라우저가 정하는 규칙이다. 내가 고칠 수 없으니 거기에 기대지 않는 구조로 가야 한다.                                                        |
| XSS와 CSRF                | XSS는 내 페이지 안에서 남의 스크립트가 도는 것, CSRF는 남의 페이지가 내 브라우저로 요청을 보내게 하는 것이다. HttpOnly는 XSS가 토큰을 들고 나가는 것만 막는다. |
| access와 refresh          | access는 털려도 금방 죽는다. refresh가 털리면 access를 계속 찍어 낸다. 숨길 가치가 큰 쪽은 refresh다.                                                          |
| refresh token 회전        | 재발급하면 refresh도 새것으로 바뀐다. 새 값을 쿠키에 옮겨 담는 것까지는 챙겼는데, 옛 값으로 동시에 들어온 요청이 어떻게 되는지는 생각하지 못했다.              |
| single-flight와 Web Locks | 같은 요청이 겹치면 하나만 보내고 결과를 나눠 쓰는 것이다. 탭 안에서는 변수 하나로 되는데, 탭끼리는 `navigator.locks`가 있어야 한다.                            |

쿠키의 보안 속성이 왜 전부 기본으로 꺼져 있는지도 찾아봤다. 쿠키는 동일 출처 정책보다 먼저 생겼고, 안전장치는 나중에 하나씩 덧붙었다. 원래 동작을 바꾸면 기존 웹이 깨지니, 안전한 쪽은 개발자가 직접 켜야 한다. HttpOnly도 그중 하나였다.

## 배운 것

1. **HttpOnly는 읽기를 막지 보내기를 막지 않는다.** XSS로 토큰을 들고 나가는 길은 막지만, CSRF와는 상관이 없다.
2. **쿠키 하나를 옮기면 심는 곳, 읽는 곳, 지우는 곳이 다 따라 움직인다.** 하나라도 어긋나면 쿠키가 두 개가 되거나 로그아웃 뒤에 남는다.
3. **한 공격을 막으려고 구조를 바꾸면 다른 공격 면이 생긴다.** 교환을 서버 라우트로 옮기자 새 길이 열렸다. 공격자가 자기 계정의 코드를 담은 form을 다른 사이트에 두면, 피해자가 그 페이지를 여는 순간 서버가 공격자 계정의 쿠키를 피해자 브라우저에 심는다(로그인 CSRF). 라우트가 같은 오리진의 JSON 요청만 받도록 해서 막았다. OAuth가 왜 `state` 값을 두는지 이때 처음 실감했다.
4. **실패 응답의 뜻을 하나로 단정하지 말자.** 401을 "죽은 토큰"으로 읽은 규칙 하나가 경합을 전체 로그아웃으로 키웠다. 삭제처럼 되돌릴 수 없는 처리는 그 뜻이 하나뿐일 때만 한다.
5. **같이 쓰는 단위만큼 잠가야 한다.** 쿠키는 브라우저의 모든 탭이 같이 쓰는데 잠금은 탭 하나였다. 자원의 범위와 잠금의 범위가 다르면 그 틈에서 경합이 난다.
6. **리뷰보다 두 줄짜리 실험이 먼저 찾았다.** 여러 번 리뷰를 거친 코드였다. 문제는 콘솔에서 같은 요청을 동시에 두 번 보내 보고서야 드러났다. "동시에 두 번 오면 어떻게 되는가"는 인증 경로마다 물어야 하는 질문이다.
7. **검증 환경이 운영과 같은 사이트 경계를 갖는지부터 본다.** 개발 환경에서는 서비스와 인증 서버가 같은 사이트라 쿠키가 퍼스트파티로 실렸다. 운영의 크로스사이트 조건을 재현하지 못하니, 문제가 있어도 개발 환경에서는 보이지 않는다. 나중에 검증 환경을 직접 구성하게 된다면, 운영과 같은 사이트 경계가 나오도록 도메인부터 설계하려 한다.
8. **모르는 것부터 정의하고 시작하라.** 첫날 한 일은 내가 뭘 모르는지 목록을 만드는 것이었다. 일반 지식, 내 시스템, 상대 시스템(인증 서버) 세 갈래로 나눴고, 개념마다 "이걸 왜 알아야 하나"부터 납득하고 넘어갔다. 그러자 인증 서버 팀에 보낼 질문이 세 개로 줄었다. 돌아가는 것 같아도, 모르는 것을 빨리 드러내고 채워 나가는 쪽이 결국 비용이 가장 적었다.

## 앞으로 생각해 볼 것

- **전면 BFF로 갈 것인가.** 지금 구조는 IETF 초안 [OAuth 2.0 for Browser-Based Applications](https://datatracker.ietf.org/doc/draft-ietf-oauth-browser-based-apps/)가 말하는 Token-Mediating Backend에 가깝다. 오래 사는 refresh는 서버가 쥐고, 짧은 access만 JS에 준다. access까지 숨기려면 모든 호출을 서버가 전달해야 하고, 쿠키에 더 기댈수록 CSRF 방어가 더 중요해진다. 지금은 JS가 헤더에 토큰을 직접 실어서, 다른 사이트가 보낸 요청에는 인증이 따라가지 않는다. BFF로 가면 그 내성을 잃는다.
- **토큰을 어디에 둘지는 누가 그 토큰을 쓰느냐로 정한다.** refresh는 서버만 써서 숨겨도 잃을 게 없었다. access는 JS가 매 요청에 써서 숨기는 순간 동작이 깨진다. 노출을 받아들이는 대신 수명을 짧게 둔다.
- **바꿀 수 없는 것에 기대지 않는다.** 브라우저 정책은 계속 바뀐다. Safari는 2020년에 서드파티 쿠키를 막았고, Chrome은 막겠다고 했다가 계획을 접었다. 그 정책에 기대는 설계는 언젠가 또 깨진다.
- **인증은 FE와 BE 경계에 걸쳐 있다.** FE 개발자와 "이걸 BE에서 하면 되지 않냐"는 이야기를 나눴다. BE에서도 할 수는 있었다. 그래도 쿠키를 심고 읽고 지우는 쪽이 한 서버에 있어야 규칙이 어긋나지 않는다고 보고 이번에는 Next.js 서버에 뒀다. 한쪽 레포만 보면 이 판단을 내리기 어렵다. 백엔드 개발자가 프론트 레포의 인증을 만져 본 게 이번에 얻은 가장 큰 경험이다.

HttpOnly 하나 붙이는 데 사흘이 걸렸다. 그 사흘의 대부분은 코드가 아니라 질문이었다. 사실 가장 값진 질문은 배포한 뒤에 나왔다. 동시에 두 번 오면 어떻게 되는가... race condition과 동시성을 언제나 고려하자. 😂
